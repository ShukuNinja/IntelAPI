# API_CONTRACT.md

**Project:** API Intelligence Platform  
**Status:** Proposed MVP contract; subordinate to `SOURCE_OF_TRUTH.md` and `TECHNICAL_DESIGN.md`  
**Version:** 1.0  
**Last updated:** 2026-10-16  
**Base path:** `/api/v1`

> This document defines the proposed HTTP interface between the React frontend and FastAPI backend. It is a contract for implementation, not a claim that these routes already exist. Where a detail is not fixed by the source-of-truth documents, the choice below is a recommended default. Record consequential changes and keep the frontend, backend, generated OpenAPI schema, and tests synchronized.

## 1. Contract Rules

- All application routes are under `/api/v1`, except the root health/readiness endpoints if deployment tooling requires otherwise.
- JSON is the default request and response format. OpenAPI file upload uses `multipart/form-data`.
- Resource IDs are UUID strings. Timestamps are ISO 8601 UTC values.
- Request and response schemas are Pydantic models. Do not expose SQLAlchemy models directly.
- Authentication uses the server-side application session described in `TECHNICAL_DESIGN.md`; browser requests include credentials. Do not put session IDs or provider secrets in JSON responses.
- Every project-owned resource is authorized server-side. A client-provided `user_id` is never proof of ownership.
- Use consistent pagination for list endpoints: `limit` and `offset`. Default `limit=50`; maximum `limit=100`. History/evidence lists may migrate to cursor pagination if needed, but do not mix pagination schemes without documenting it.
- Unknown fields should be rejected for security-sensitive configuration models where practical. Ordinary API target bodies must remain arbitrary JSON or text as appropriate.
- Omit internal stack traces, database details, secrets, and raw provider errors from client responses.
- Mutating requests must not be retried automatically by the frontend unless the operation is safe or has an explicit idempotency strategy.
- OpenAPI generated by FastAPI is the machine-readable implementation contract. CI should detect material drift from this document and run request/response contract tests.

## 2. Common Types

### 2.1 Identifiers and timestamps

```json
{
  "id": "8f9f4c3a-0f57-4a8c-8a9f-3d7c9a8e0a12",
  "created_at": "2026-10-16T09:30:00Z",
  "updated_at": "2026-10-16T09:30:00Z"
}
```

Example values are illustrative only. IDs are generated by the server. Clients must not depend on a particular UUID version or timestamp precision.

### 2.2 Error envelope

All expected API errors use this shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request is invalid.",
    "details": [
      { "field": "name", "issue": "Field is required." }
    ],
    "request_id": "req_01J..."
  }
}
```

- `error.code`: stable machine-readable string.
- `error.message`: safe, user-facing summary.
- `error.details`: optional array/object with safe field-level or policy details; never include credentials or unrestricted target response bodies.
- `error.request_id`: optional correlation identifier, also included in server logs.

Recommended codes include `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `TARGET_BLOCKED`, `TARGET_TIMEOUT`, `TARGET_RESPONSE_TOO_LARGE`, `SPEC_IMPORT_FAILED`, `LLM_UNAVAILABLE`, `BUDGET_EXCEEDED`, and `INTERNAL_ERROR`.

### 2.3 Pagination

List endpoints accept:

- `limit`: integer, default `50`, range `1..100`.
- `offset`: integer, default `0`, minimum `0`.

Paginated responses use:

```json
{
  "items": [],
  "pagination": { "limit": 50, "offset": 0, "total": 0 }
}
```

If obtaining an exact total is expensive, a future contract revision may replace `total` with `has_more`; do not silently vary response shape by endpoint.

## 3. Authentication and Session

### `GET /auth/google/config`
Returns only browser-safe configuration needed to initialize Google sign-in.

**Auth:** public.  
**Response `200`:**

```json
{ "client_id": "configured-google-oauth-client-id" }
```

Do not return client secrets or server configuration.

### `POST /auth/google/session`
Verifies a Google ID token and creates the application session.

**Auth:** public, rate-limited.  
**Request:**

```json
{ "id_token": "<google-id-token>" }
```

**Response `200`:** sets the application session cookie and returns:

```json
{
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "display_name": "Example User",
    "avatar_url": null
  }
}
```

The backend validates the Google token signature, issuer, audience, expiry, and required claims. Use the stable Google subject to link identity. Never log or persist the incoming ID token as an application session credential. Cookie flags and CSRF policy follow `TECHNICAL_DESIGN.md`.

### `GET /auth/me`
Returns the authenticated application user.

**Auth:** required. **Response `200`:** same `user` object as above.

### `POST /auth/logout`
Invalidates the current server-side session and clears the cookie.

**Auth:** required. **Response `204`:** no body.

### `GET /health/live`
Liveness probe; indicates the API process is running. Does not imply database or target API health.

**Auth:** none. **Response `200`:** `{ "status": "ok" }`.

### `GET /health/ready`
Readiness probe; checks dependencies required for the API to serve requests, at minimum database connectivity.

**Auth:** internal/deployment use; deployment policy may restrict access. **Response `200`:** `{ "status": "ready" }`; `503` when not ready. Do not expose secrets or detailed dependency diagnostics publicly.

## 4. Projects

Projects are the authorization boundary for saved API assets, specifications, campaigns, and evidence.

### `GET /projects`
Lists projects visible to the current user.

**Auth:** required. **Query:** `limit`, `offset`.  
**Response `200`:** paginated `items` of:

```json
{
  "id": "uuid",
  "name": "Payments API",
  "description": "Optional description",
  "created_at": "2026-10-16T09:30:00Z",
  "updated_at": "2026-10-16T09:30:00Z"
}
```

### `POST /projects`
Creates a project owned by the current user.

**Request:** `{ "name": "Payments API", "description": "Optional description" }`  
`name`: required, trimmed, 1–120 characters. `description`: optional, max 2,000 characters.  
**Response:** `201` project object.

### `GET /projects/{project_id}`
Returns one project. **Response:** `200`; `404` if absent or not visible to the caller.

### `PATCH /projects/{project_id}`
Updates `name` and/or `description`. At least one supported field is required. **Response:** `200` updated project.

### `DELETE /projects/{project_id}`
Deletes a project according to the explicit cascade/retention policy in `DATABASE_DESIGN.md`. Because deletion can remove evidence, require a confirmation mechanism in the UI. **Response:** `204`; `404` if not visible; `409` if deletion is blocked by policy.

## 5. Collections and Saved Requests

### `GET /projects/{project_id}/collections`
Lists collections in a project. Query: `limit`, `offset`. **Response:** paginated collection objects (`id`, `project_id`, `name`, optional `description`, timestamps).

### `POST /projects/{project_id}/collections`
Creates a collection. Request: `{ "name": "Billing", "description": null }`. Name is required and 1–120 characters. **Response:** `201` collection object.

### `PATCH /collections/{collection_id}`
Updates collection name/description. **Response:** `200` collection object.

### `DELETE /collections/{collection_id}`
Deletes a collection. Saved requests must either be detached or deleted according to the documented database policy; do not silently lose request definitions. **Response:** `204`.

### `GET /projects/{project_id}/requests`
Lists saved requests. Optional filters: `collection_id`, `limit`, `offset`. **Response:** paginated saved-request objects.

### `POST /projects/{project_id}/requests`
Creates a saved request. **Request:**

```json
{
  "name": "Get payment",
  "collection_id": "uuid-or-null",
  "method": "GET",
  "url_template": "https://api.example.com/payments/{payment_id}",
  "path_params": { "payment_id": "pay_123" },
  "query_params": [{ "key": "expand", "value": "items", "enabled": true }],
  "headers": [{ "key": "Accept", "value": "application/json", "enabled": true }],
  "body": { "mode": "none", "content_type": null, "raw": null },
  "auth": { "type": "none", "config": {} }
}
```

Rules:
- `method`: one of `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.
- `url_template`: required string, maximum 8,192 characters; must use `http` or `https` when resolved for execution.
- `path_params`, query/header entries, body, and auth are configuration only. Secrets must be redacted from responses where appropriate.
- Query and header entries preserve ordering where the UI requires it. Disabled entries are not sent.
- Initial auth types: `none`, `bearer`, `basic`, and `api_key` (header or query placement only). OAuth flows are not part of the baseline MVP unless explicitly approved.
- Body modes: `none`, `raw`, and `json`; form-data/binary modes may be added only if time and tests permit.

**Response:** `201` saved-request object, including configuration safe to display. Never return resolved secret values in clear text.

### `GET /requests/{request_id}`
Returns a saved request. **Response:** `200`.

### `PATCH /requests/{request_id}`
Updates one or more saved-request fields. **Response:** `200` updated object.

### `DELETE /requests/{request_id}`
Deletes the saved request. Historical executions must retain their own execution snapshot and must not be rewritten. **Response:** `204`.

## 6. Environments

### `GET /projects/{project_id}/environments`
Lists environment metadata. **Response:** paginated objects with `id`, `name`, timestamps; secret values are not returned in list responses.

### `POST /projects/{project_id}/environments`
Creates an environment. Request: `{ "name": "Development", "variables": [{"key":"base_url","value":"https://api.example.com","is_secret":false}] }`. **Response:** `201` environment metadata and non-secret variables only.

### `GET /environments/{environment_id}`
Returns environment metadata and non-secret values. Secret values must be masked or omitted.

### `PATCH /environments/{environment_id}`
Updates name and/or variables. Secret values are write-only after creation: clients may set or replace them but cannot retrieve their stored plaintext. **Response:** `200` safe representation.

### `DELETE /environments/{environment_id}`
Deletes the environment. **Response:** `204`.

### Variable resolution
Variables use an explicit syntax such as `{{variable_name}}`. Resolution is performed server-side immediately before execution. Unknown variables cause a validation error by default rather than being sent literally. Secret values must be redacted from request/response evidence and logs. Exact escaping rules should be implemented once in a shared resolver and covered by tests.

## 7. Manual Request Execution and History

### `POST /requests/execute`
Executes a one-off request using the shared outbound execution service. It may accept an unsaved request definition; saved request execution can include `saved_request_id`.

**Auth:** required. **Request:**

```json
{
  "project_id": "uuid",
  "saved_request_id": null,
  "environment_id": null,
  "request": {
    "method": "GET",
    "url": "https://api.example.com/health",
    "path_params": {},
    "query_params": [],
    "headers": [],
    "body": { "mode": "none", "content_type": null, "raw": null },
    "auth": { "type": "none", "config": {} }
  }
}
```

**Response `200`:**

```json
{
  "execution": {
    "id": "uuid",
    "outcome": "http_response",
    "status_code": 200,
    "duration_ms": 83,
    "response_headers": [{ "key": "content-type", "value": "application/json" }],
    "body": { "kind": "json", "value": { "status": "ok" }, "truncated": false },
    "transport_error": null,
    "started_at": "2026-10-16T09:30:00Z",
    "completed_at": "2026-10-16T09:30:00Z"
  }
}
```

`outcome` is one of `http_response`, `timeout`, `connection_error`, `blocked_by_policy`, `response_too_large`, or `execution_error`. A received non-2xx HTTP response is still `http_response`; the HTTP status is separate from transport outcome. Response body capture is bounded and may be truncated. Sensitive response headers and credentials are redacted. A blocked target or transport failure should return a structured execution result where possible rather than an unhandled server error.

Safety policy:
- The request must be associated with a project the caller can access.
- Only the shared execution service can issue outbound requests.
- Apply SSRF controls, timeouts, request/response size caps, redirect revalidation, TLS verification, and request budgets from `TECHNICAL_DESIGN.md`.
- Manual execution must not allow arbitrary target code or disable production safeguards.

### `GET /projects/{project_id}/history`
Lists recent executions for the project. Query: `limit`, `offset`; optional filters `method`, `status_code`, `outcome`, `from`, `to`. **Response:** paginated execution summaries, excluding unredacted secrets and large body content.

### `GET /executions/{execution_id}`
Returns one execution and its bounded, redacted response capture. **Response:** `200`.

### `DELETE /executions/{execution_id}`
Optional for MVP; if implemented, deletion must respect evidence retention and campaign linkage. If evidence depends on an execution, prefer retention/redaction controls over destructive deletion. Do not implement this route unless policy is settled.

## 8. Health Checks

### `GET /projects/{project_id}/health-checks`
Lists configured health checks. **Response:** paginated health-check objects (`id`, `name`, request definition/reference, optional assertion definitions, timestamps).

### `POST /projects/{project_id}/health-checks`
Creates a named check. Request:

```json
{
  "name": "API readiness",
  "request": {
    "method": "GET",
    "url": "https://api.example.com/health",
    "path_params": {}, "query_params": [], "headers": [],
    "body": { "mode": "none", "content_type": null, "raw": null },
    "auth": { "type": "none", "config": {} }
  },
  "assertions": [
    { "kind": "status_code_in", "expected": [200] },
    { "kind": "json_path_equals", "path": "$.status", "expected": "ok" }
  ]
}
```

The assertion set is intentionally limited to deterministic, documented operators. Do not evaluate arbitrary user-supplied scripts.

### `POST /health-checks/{health_check_id}/run`
Runs the check immediately through the shared execution service and returns the execution summary plus assertion results. **Response:** `200`. This is a synchronous single check with strict request timeout; it is not a continuous-monitoring guarantee.

### `GET /health-checks/{health_check_id}/runs`
Lists prior runs. **Response:** paginated summaries.

### `DELETE /health-checks/{health_check_id}`
Deletes a configured check while retaining historical evidence according to retention policy. **Response:** `204`.

## 9. OpenAPI Specification and API Explorer

### `POST /projects/{project_id}/specifications/import`
Imports an OpenAPI document from an uploaded file.

**Content type:** `multipart/form-data`; field `file`.  
**Response `201`:**

```json
{
  "specification": {
    "id": "uuid",
    "project_id": "uuid",
    "title": "Payments API",
    "openapi_version": "3.1.0",
    "version_label": "1.4.2",
    "content_hash": "sha256:...",
    "parse_status": "completed",
    "warnings": [],
    "created_at": "2026-10-16T09:30:00Z"
  },
  "summary": { "operation_count": 24, "schema_count": 18, "warning_count": 0 }

```

Parsing must not execute operations or automatically fetch external `$ref` URLs. Enforce file-size and parse-time limits. Unsupported constructs must produce explicit warnings or a failed import status.

### `POST /projects/{project_id}/specifications/import-url`
Optional MVP endpoint for importing from a URL. Implement only with SSRF-safe URL fetching, destination validation, bounded redirects, and response-size/time limits. If these controls are not ready, omit the route and support file upload only.

**Request:** `{ "url": "https://docs.example.com/openapi.json" }`. **Response:** same shape as file import.

### `GET /projects/{project_id}/specifications`
Lists imported specification versions. **Response:** paginated metadata.

### `GET /specifications/{specification_id}`
Returns specification metadata, import summary, and warnings. Do not return arbitrary external URLs as trusted links.

### `GET /specifications/{specification_id}/operations`
Lists normalized operations. Query: `limit`, `offset`, optional `tag`, `method`, `path_search`. **Response:**

```json
{
  "items": [
    {
      "id": "uuid",
      "method": "GET",
      "path": "/payments/{payment_id}",
      "operation_id": "getPayment",
      "summary": "Retrieve a payment",
      "tags": ["Payments"],
      "parameters": [],
      "request_body_schema": null,
      "responses": [{ "status_code": "200", "description": "Payment", "schema": {} }],
      "provenance": "DECLARED"
    }
  ],
  "pagination": { "limit": 50, "offset": 0, "total": 1 }
}
```

Schema payloads should be normalized and size-bounded; do not duplicate the entire imported document in every operation response.

### `GET /operations/{operation_id}`
Returns the full normalized operation detail, including parameter definitions and request/response schema references. **Response:** `200`.

### `DELETE /specifications/{specification_id}`
Deletes or archives a specification according to retention policy. Existing campaign/execution evidence must retain the specification version/hash used. **Response:** `204` or `409` if policy blocks deletion.

### Provenance enum
Use `DECLARED`, `EXTRACTED`, `OBSERVED`, and `INFERRED` for facts or knowledge items, as defined in `TECHNICAL_DESIGN.md`. Never label an inferred hypothesis as declared contract.

## 10. Test Campaigns

Campaigns are durable asynchronous workflows. Creation must return promptly; the client polls status rather than keeping a request open while tests execute.

### Campaign state machine

Allowed states:

- `queued`: persisted and waiting for a worker claim.
- `running`: claimed by a worker and executing within configured limits.
- `completed`: all planned work ended normally or the campaign reached a defined terminal budget condition.
- `failed`: campaign could not complete due to an unrecoverable internal/configuration error.
- `cancelled`: user requested cancellation and the worker reached a safe stopping point.

Allowed transitions:

```text
queued -> running | cancelled | failed
running -> completed | failed | cancelled
```

Terminal states (`completed`, `failed`, `cancelled`) cannot transition back to active states. A rerun creates a new campaign rather than resetting the historical record. If a worker crashes, recovery logic must reclaim or safely fail the campaign based on persisted lease/heartbeat state.

### `GET /projects/{project_id}/campaigns`
Lists campaigns. Query: `limit`, `offset`, optional `state`, `created_after`, `created_before`. **Response:** paginated campaign summaries.

### `POST /projects/{project_id}/campaigns`
Creates and queues a campaign.

**Request:**

```json
{
  "name": "Payments API exploration",
  "specification_id": "uuid-or-null",
  "environment_id": "uuid-or-null",
  "target_operation_ids": ["uuid"],
  "mode": "adaptive",
  "test_categories": ["positive", "negative", "boundary", "schema", "workflow"],
  "max_requests": 100,
  "max_iterations": 10,
  "deadline_seconds": 900,
  "per_request_timeout_seconds": 15,
  "max_response_bytes": 1048576,
  "allow_llm": false
}
```

Rules:
- `name`: required, 1–120 characters.
- `mode`: `baseline` or `adaptive`.
- `test_categories`: non-empty subset of supported categories.
- `max_requests`, `max_iterations`, deadline, per-request timeout, and response limit must be bounded by server-configured hard maxima. The server clamps only where the behavior is explicit; otherwise it rejects invalid values with `VALIDATION_ERROR`.
- `target_operation_ids` must belong to the selected project/specification. If omitted and no specification is available, the request must include a supported explicit target definition or be rejected. Do not guess a target.
- `allow_llm` is opt-in. If false, the campaign uses deterministic candidate generation and heuristics. If true but no provider is configured, return a clear validation/configuration error or run only the explicitly supported deterministic fallback and report that LLM assistance was unavailable; never fabricate AI output.

**Response `202 Accepted`:**

```json
{
  "campaign": {
    "id": "uuid",
    "project_id": "uuid",
    "name": "Payments API exploration",
    "state": "queued",
    "progress": { "requests_executed": 0, "tests_generated": 0, "tests_remaining_estimate": null },
    "limits": { "max_requests": 100, "max_iterations": 10 },
    "created_at": "2026-10-16T09:30:00Z",
    "started_at": null,
    "completed_at": null
  }
}
```

### `GET /campaigns/{campaign_id}`
Returns campaign state, safe configuration, progress, summary counters, timestamps, and a terminal failure code/message if applicable. Do not expose stack traces or secrets.

### `POST /campaigns/{campaign_id}/cancel`
Requests cancellation. **Response:** `202` with current state. If already terminal, return `409 CONFLICT` or a documented idempotent success; choose one behavior and test it consistently. Cancellation is cooperative: an in-flight HTTP request may finish before the worker stops, but no new request should start after cancellation is observed.

### `GET /campaigns/{campaign_id}/tests`
Lists generated test cases. Query: `limit`, `offset`, optional `category`, `status`. Each item includes `id`, target operation, category, rationale, generation source, validation state, execution state, and timestamps. Do not expose hidden chain-of-thought or provider-private reasoning; rationale should be a concise evidence-based explanation.

### `GET /campaigns/{campaign_id}/executions`
Lists executions associated with the campaign. **Response:** paginated execution summaries.

### `GET /campaigns/{campaign_id}/report`
Returns a report summary: test counts, assertion outcomes, findings counts, defined coverage measures, budget usage, campaign status, and known limitations. **Response:** `200` when a report can be produced, including partial reports for failed/cancelled campaigns when evidence exists.

## 11. Findings and Evidence

### `GET /projects/{project_id}/findings`
Lists findings for a project. Query: `limit`, `offset`, optional `campaign_id`, `severity`, `status`, `category`, `operation_id`. **Response:** paginated findings.

Finding object:

```json
{
  "id": "uuid",
  "project_id": "uuid",
  "campaign_id": "uuid-or-null",
  "title": "Response differs from declared schema",
  "category": "contract_mismatch",
  "severity": "medium",
  "status": "open",
  "summary": "Observed response omitted a required field from the imported schema.",
  "confidence": 0.82,
  "provenance": "OBSERVED",
  "evidence_count": 2,
  "created_at": "2026-10-16T09:30:00Z",
  "updated_at": "2026-10-16T09:30:00Z"
}
```

Severity values: `info`, `low`, `medium`, `high`, `critical`. Status values: `open`, `investigating`, `accepted`, `resolved`, `false_positive`. Confidence is optional and must not be presented as statistical certainty unless calibrated. A finding is a supported observation or hypothesis, not automatically a confirmed defect.

### `GET /findings/{finding_id}`
Returns finding detail and linked evidence references. **Response:** `200`.

### `PATCH /findings/{finding_id}`
Allows updates only to user-managed fields such as `status` and optionally `severity` with audit metadata. The system-generated observation, provenance, and raw execution record must not be overwritten. **Response:** `200` updated finding.

### `GET /findings/{finding_id}/evidence`
Lists evidence linked to a finding. **Response:** paginated evidence references.

### `GET /evidence/{evidence_id}`
Returns an authorized, redacted evidence record. Evidence can reference execution IDs, response excerpts/JSON paths, specification version and JSON Pointer, assertion results, and adaptive selection rationale. Body excerpts must respect capture and retention limits.

### `GET /projects/{project_id}/evidence`
Lists evidence for the project. Query: `limit`, `offset`, optional `campaign_id`, `execution_id`, `finding_id`, and provenance. **Response:** paginated evidence references.

### Evidence integrity
- Preserve raw execution outcomes separately from derived analysis.
- Record the specification version/hash and test case used for each relevant execution.
- Record why an adaptive follow-up was selected, including referenced evidence IDs and a concise rationale.
- Never modify evidence in place to make a later interpretation look like the original observation. Corrections should be represented as new analysis records or versioned fields.

## 13. Status Codes and Error Mapping

| HTTP status | Use |
|---|---|
| `200 OK` | Successful read/update or synchronous execution result |
| `201 Created` | Resource created or specification imported |
| `202 Accepted` | Campaign queued or cancellation requested |
| `204 No Content` | Successful logout/deletion with no response body |
| `400 Bad Request` | Malformed request that cannot be interpreted |
| `401 Unauthorized` | Missing, expired, or invalid application session |
| `403 Forbidden` | Authenticated user lacks permission, if resource existence can safely be disclosed |
| `404 Not Found` | Resource absent or intentionally concealed due to ownership policy |
| `409 Conflict` | Invalid state transition, deletion conflict, or duplicate/competing operation |
| `413 Payload Too Large` | Request/specification exceeds configured size limit |
| `422 Unprocessable Entity` | Schema validation or semantically invalid configuration |
| `429 Too Many Requests` | Rate/request budget limit exceeded; include `Retry-After` where useful |
| `502 Bad Gateway` | Optional mapping for upstream transport/protocol failure when not returned as a structured execution result |
| `503 Service Unavailable` | Required dependency/provider unavailable for an operation that cannot fall back |
| `504 Gateway Timeout` | API-side deadline exceeded where a structured execution result is not appropriate |

For target execution, prefer a successful API response containing a typed `execution.outcome` for expected target failures (timeout, connection error, blocked destination, oversized response). Reserve API-level errors for invalid input, authorization failures, or cases where no execution record can safely be created. This keeps target behavior distinct from platform API failure.

## 14. Rate Limits and Resource Budgets

- Apply rate limits to authentication, manual execution, specification imports, campaign creation, and expensive LLM-assisted operations.
- Enforce server-side hard limits even if the frontend validates values.
- A campaign request budget counts actual outbound target requests, including retries if retries are enabled. Prefer no automatic target-request retries in the MVP; if retries are added, count every attempt.
- Enforce per-request timeout, total campaign deadline, response byte limit, and concurrency cap.
- Return `429` with a stable error code when a user-level/platform-level budget prevents starting work. If a running campaign exhausts its configured budget, finish it with a documented terminal reason and report budget usage.

## 15. Idempotency, Concurrency, and State Transitions

- `GET`, `HEAD`, and `OPTIONS` should be safe according to HTTP semantics; the platform must not assume the target API itself is well behaved.
- Resource creation endpoints are not automatically idempotent. If retries by clients are likely, add an `Idempotency-Key` contract and persistent deduplication before enabling automatic retries.
- Campaign creation must persist the campaign and queue/claim metadata transactionally enough that a created campaign cannot be silently lost. A duplicate submission may create two campaigns unless idempotency is implemented; the UI should prevent accidental double submission.
- Campaign state transitions must be validated in the domain service and guarded against concurrent worker updates.
- Cancellation must be cooperative and persisted. No new target request should begin after cancellation is observed.
- Updating or deleting a saved request must not rewrite historical execution snapshots.

## 16. Contract Testing and OpenAPI

Backend implementation requirements:

1. Define all request/response models explicitly in Pydantic.
2. Give every route a documented response model and status codes.
3. Use one error handler to normalize validation, authorization, and unexpected errors into the agreed envelope; FastAPI's default validation response must not leak a divergent shape.
4. Generate the OpenAPI document from FastAPI and validate that it covers all implemented routes.
5. Add tests for success, invalid payload, unauthenticated access, cross-project ownership denial, and documented error responses.
6. Add campaign transition tests and outbound execution policy tests.
7. Add frontend type generation or contract compatibility checks in CI before parallel implementation expands.
8. Do not treat a manually written endpoint list as a substitute for route-level tests.

## 17. Explicitly Deferred Decisions

These decisions must be finalized in implementation planning or `DATABASE_DESIGN.md`/ADRs; do not invent inconsistent behavior in individual modules:

- Exact table-level deletion and evidence-retention rules.
- Whether API-key auth supports query placement in addition to headers in the initial UI.
- Whether multipart/form-data and binary request bodies fit the MVP schedule.
- Exact assertion operator set and JSONPath implementation.
- Whether specification URL import and cURL import are included in the first release.
- Exact server-side rate limits and hard budget maxima, configured centrally.
- Whether findings require a separate audit-history table for user status changes.
- Whether cursor pagination is needed for high-volume evidence/history.
- Whether idempotency keys are implemented for campaign creation.

If a deferred feature is not implemented, omit its route or reject it explicitly. Do not return mock success for unimplemented behavior.
