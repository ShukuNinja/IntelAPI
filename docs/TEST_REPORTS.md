# Test reports

Generation reports are persisted per project/specification and are distinct from runtime execution reports. They list endpoint coverage, candidate count/IDs, rule kind, rationale, mutation preview, and `preview` validation status. Their cap and truncation behavior are documented in [TEST_GENERATION.md](TEST_GENERATION.md). Reports can be reopened and exported as JSON, Markdown, or CSV.

Candidate execution reports are persisted separately from generation reports. They include operation/candidate identity, HTTP outcome/status, duration, response size and allowlisted response headers, explicit status assertions, contract observations for undocumented statuses/content types, limited response-schema mismatch paths, and the bounded deterministic feedback decision. JSON Schema references and composition keywords are reported as skipped analysis paths. Observations are not classified as confirmed defects. See [FEEDBACK_POLICY.md](FEEDBACK_POLICY.md) for branches and limits.

The response body is returned to the active request UI, used in memory for the bounded schema check and JSON Pointer presence/type assertions, and never persisted in execution history or reports. User assertions can compare only the `content-type`, `content-length`, and `date` response headers; arbitrary headers and response-body value equality are not supported. Execution history stores only safe method/origin/candidate metadata and outcome fields. Candidate run reports can be reopened in Request History and exported as JSON, Markdown, or CSV. PostgreSQL and cross-restart verification remain incomplete.

Specification readiness is a deterministic, read-only analysis over the saved source document and normalized operation list. Findings include severity, rule code, message, and source JSON Pointer. Its scope is documented completeness; it does not establish security or runtime correctness and is not persisted as a separate report record.

The Findings & Evidence workflow derives review items only from persisted contract observations and failed assertions. A user can record a confirmed defect, false positive, or accepted risk with an optional note. The underlying observation is not automatically classified, and response body values are not added to the finding record.
